## Style & conventions (terse)

- No flowery language in commits; short subject + minimal body.
- No `Co-Authored-By` or `Author:` trailers in git commits. Use a
  conventional-commits style subject and body only.
- Default to no comments; only add when WHY is non-obvious.
- Surgical changes — don't refactor unrelated code.
- UUPS upgrades: append-only storage; `pnpm storage:check` MUST pass.
- For FHE / crypto / multichain: read docs + source, never guess.
- Frontend signing: pass through `useEmailAuthSigner` (it handles both
  EOA and passkey-AA paths).
- Contract calls from frontend: prefer `useUnifiedWrite` /
  `unifiedWriteBatch` so the EOA + AA + paymaster modes are all handled.

## Hard operational rules (locked)

These are non-negotiables for any agent working on Blank. They are
tuned for Blank's reality: Fhenix CoFHE, Sepolia + Base Sepolia,
passkey-AA + EOA paths, invoices, escrow, payment links, proofs, and
private payment workflows.

### A. No compromise

If a feature is on the build list and is testable, ship it. If it is
"cool but unverifiable," push back and propose something verifiable
instead. Default to the strongest practical implementation, test, and
UX path available. The easiest path is rarely the right one.

Production-ready option rule: if there are multiple plausible paths,
choose the one that makes the product more useful, trustworthy, smooth,
and verifiable. Do not choose the easiest path if it leaves the feature
weaker, less polished, or harder to prove.

The only normal blocker is money. Anything that does not require real
funding, paid quota, a third-party approval, or hardware we do not have
is a "yes, build it" item. "Hard," "takes time," or "needs careful
automation" is not blocked.

### B. Test = easy to verify by USING it

A feature you cannot run in one command (CLI, hardhat task) or one
URL (public invoice, payment link, receipt, proof page) is a feature
you cannot prove. The right proof shape is: run the flow, see the
visible result, get a real URL, and get a real on-chain transaction
hash or explorer link.

For UI features, CLI proof is not enough. The user-facing surface, the
underlying contract or API path, and the real side effect must all be
proven through the UI path. If a user can see the feature, they must be
able to use it without hidden setup beyond the documented wallet, chain,
and funding requirements.

### C. No lazy blocked

Before marking anything blocked, prove you tried the strongest
available method: real Playwright + real MetaMask extension, hardhat
task, multi-wallet flow, multi-session flow, viem client, backend
harness, protocol-level test, or code-level verification. "Hard" or
"takes time" is not blocked. "Needs a real phone, paid quota,
third-party token, funded deployer, or unavailable external UI" is.

### D. Brutal honesty about half-baked

When a feature exists in code but the UX, surface, or end-to-end
story is incomplete, say it explicitly first — before recommending
it as a strength or proposing to extend it. Half-baked surfaced
late = wasted strategy time. Examples we have actually had:
- Stealth payments existed but the scanner was missing → surfaced
  as a critical gap, then verified already shipped (Phase 9.4).
- BusinessHub escrow stored amounts in plaintext → surfaced as a
  privacy contradiction, then fixed via `EncryptedEscrow.sol`.

### E. No half-baked anything

No half-baked build, feature, UI/UX, testing, polish, docs, demo
flow, payment links, invoice links, proof links, wallet flow, mobile view, error
states, loading states, empty states, contract upgrade, fee path,
multi-wallet testing, mainnet readiness, competitor comparison,
or submission package.

No fake green status. No "works on my path." No connect-only
testing. No screenshot-only proof. No selector-only QA. No claim
without an on-chain transaction hash.

No UI button without real use. No feature without PMF. Function,
proof, UX, and testing land together. If users can see it, it must
work, fail honestly, and have a proof path.

## PMF filter — three checks before building

Every feature must pass all three:

1. **Is it good?** Not "cool" — useful. Would a real user care?
2. **Is it testable?** Can I verify it works by running it once with
   either a hardhat task or a real Playwright + MetaMask flow?
3. **What FHE primitive does it stretch?** Wave 4 features lean on
   `FHE.eq` (invoice match), `FHE.gte` (proof of income or payment
   thresholds), `FHE.select` (private release/refund branches), and
   `FHE.add` (running encrypted totals). Surface-level integrations
   that don't need FHE are not Blank's edge. If it is only cool with
   FHE, but not better because of FHE, push back.

If a feature passes 1+2+3, ship it. If it fails any one, push back.

UI promotion rule: when a feature exists in CLI / contracts / hooks
but not in a screen, ask whether users would honestly use it from the
UI. Add it to a screen only if it has real UI PMF. Otherwise keep it
in `tasks/` and `lib/` and document why in the task's help text.

## Writing voice — no AI slop

Anything that ships (READMEs, blog posts, milestone forms,
commit bodies, judge-facing copy, code comments, marketing tweets):

- **No em-dashes.** One clause per sentence. If you reach for `—`,
  rewrite. Use periods, commas, parentheses, colons.
- **No banned words:** delve, unlock, unleash, robust, leverage,
  empower, seamless, harness, streamline, cutting-edge,
  state-of-the-art, revolutionize. They mark a paragraph as
  AI-written on sight.
- **No three-adjective stacks** ("powerful, scalable, secure"). Pick
  the one that's true and prove it with a number.
- **No "in today's fast-paced world" / "in the realm of"** openers.
  Start with the noun that matters.
- **No symmetric bulleted slop.** If a bullet only exists to balance
  the list, kill it.
- **No marketing sandwich** (claim → flowery elaboration → restated
  claim). Make the claim once.
- **No invented quotes, fake stats, or hallucinated user
  testimonials.** "We processed $2.3M in encrypted volume" is a
  statement of fact or it's a lie; pick.
- **Show, don't adjective.** "70 unit tests" not "thoroughly tested."
  "200ms p95" not "blazingly fast." "61 receipts on Sepolia" not
  "production-ready."
- **Cut every word the sentence still works without.** Read it
  aloud. If you're embarrassed, rewrite.
- **Match Blank's voice:** terse, technical, blunt. Editorial.
  Receipts > rhetoric.

## End-to-end testing rule (the "real human" test)

A shipped feature counts as tested only when ALL of the following
hold. This is the hard gate, not a suggestion.

### F. Use the real product

- **Real MetaMask extension** loaded into Playwright via
  `--load-extension`, not a mocked wallet, not a `window.ethereum`
  injection. Drive the actual MM popups for connect, sign, switch
  chain, add network, confirm tx. The driver lives at
  `packages/app/e2e/fixtures/metamask/mm-driver.ts`.
- **Real wallet, real chain.** Sepolia + Base Sepolia for now. No
  localhost-only flows count.
- **Real on-chain side effects.** A test that produces a real tx +
  Etherscan link is the bar. A test that asserts "button clicked"
  is not. For Blank, the proof shape is a real invoice, escrow,
  payment, receipt, proof, or refund flow with a transaction hash and
  a URL a reviewer can open.

### G. Drive it like a user

- Click buttons, wait for visible state, watch transitions, read the
  proof page the user lands on.
- For multi-party flows, drive every wallet through its own MetaMask
  popup. Do not collapse a multi-party flow into a single-wallet
  shortcut.
- In Blank, multi-party means vendor to client invoice, escrow payer
  to vendor, contractor payout admin to recipient, and proof issuer to
  verifier. Do not substitute unrelated claim, shop, or crowdfund flows
  for Blank's payment flows.
- Test desktop (1280×800) AND mobile (375×812) viewports for any
  user-facing screen. Mobile is not optional.

### H. Capture proof a judge could replay

- Screenshots at every meaningful state transition: pre-action, MM
  popup open, post-confirm, final proof page. Not only the final
  state.
- Video recording of the full flow whenever the smoothness of
  transitions, loading states, or interaction feel matters. Judges
  notice how it feels, not only that it worked.
- Test wallet generation + funding lives in
  `tasks/fund-mm-test-wallet.ts` and `tasks/shield-mm-test-wallet.ts`
  so the proof flow is reproducible by anyone with the deployer key.

### I. Cover every shipped feature

If even one item from the WAVE4.md punch list has no proof line in
the Wave 4 testing TODO, the wave is not done. Edge cases count:
- Invoice link with a bogus id must show an honest error.
- Wrong invoice amount must fail closed or refund through escrow.
- Unauthorized release, refund, or proof access must reject.
- Empty input must be gated before wallet prompts or token spend.

## Completion discipline (the "do not stop" rule)

You may stop only when every shipped feature is one of:

- **verified end-to-end with proof** (screenshot or video, public
  URL that resolves on a different machine, transaction hash, or
  command output),
- **fixed and re-tested** after a regression was found, or
- **explicitly blocked with a real reason AND a concrete unblock
  action** (paid faucet quota exhausted, mainnet OG funding
  pending, no public Base Sepolia node, etc.).

"Looks like it works" is not done. "I asserted on a selector" is
not done. "Type-check passed" is not done.

### J. No partial credits

These do NOT count as end-to-end proof on their own:
- Connect-only: wallet connects but no chain write was tested.
- Screenshots-only: pixels captured but no functional flow was
  driven.
- Hardhat-task-only: terminal works but the UI surface was not
  verified.
- UI-only: screen renders but the contract path was not exercised.
- Type-check-only: code compiles but no runtime path was proven.
- Mock-only: synthetic wallet, injected ethereum, mocked threshold.

Every shipped feature needs the matched pair: **the user-facing
surface AND the underlying contract path AND the on-chain side
effect**. If any leg is missing, the feature is not shipped.

### K. Genie rule (intent, not letter)

When the user says "test it," "ship it," "make it ready," or "build
this fully," interpret the intent, not only the words. The intent
is: a real human, using the product the way a real human would,
sees a polished result, and a judge running the same flow on a
different machine arrives at the same conclusion. Do not look for
loopholes that satisfy the letter while violating the intent.

If a phrase is ambiguous (e.g. "test invoice links"), pick the
longest reasonable user journey with the strongest available method
(real MM, real wallet, real chain, video + screenshots, multi-wallet
if applicable, both viewports), not the shortest one that compiles.
Unclear instructions resolve toward the harder, more thorough
interpretation, not the easier one.

### L. Living punch-list discipline

`WAVE4.md` is the source of truth for "what's built." `WAVE4_TESTING_TODO.md`
is the source of truth for "what's tested." Every shipped feature gets
a line in both. The status updates in the same commit that ships the
feature, not a follow-up. If a feature has no line in either file, it
has no proof, so it does not exist.
